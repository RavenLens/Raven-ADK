# HITL Transport

The HITL transport connects a HITL strategy to the user interface or another
client. The transport is provided through `HITLAdapter`, which is used by both
`HITL` (`DefaultHITL`) and `AutoPilotHITL`.

A transport has two responsibilities:

1. Forward each `HITLRequest` to the UI or client together with its
   correlation id.
2. Pass the matching `HITLResponse` back to the strategy through the response
   handler registered by `HITL`.

The adapter transports requests. It does not decide whether a request is
ordinary tool approval, a question, or acceptance. That routing is determined
by the HITL strategy and its configuration. See [README.md](README.md#configuration-and-routing)
for the configuration rules and [DefaultHITL.md](DefaultHITL.md) or
[AutoPilotHITL.md](AutoPilotHITL.md) for strategy behavior.

The agent or integration retains full agility over policy. It chooses the
`toolsUsage` whitelist and chooses whether a workflow calls `emitToolUsage`, a
question tool, or `emitAcceptance`. The adapter only transports the request
after that choice has been made; it does not expand the whitelist or decide
whether the user should be asked.

Timeouts are strategy-owned. `delaysMs` and `defaultAnswer` are applied by
`HITL` around the pending correlation id; the adapter only forwards the request
and any response. When a request times out, the pending id is removed and a
late response cannot resolve that interaction.

## HITLAdapter

The interface is defined in
[DefaultHITL.ts](../../src/agent/tools/hitl/hitl-strategies/DefaultHITL.ts):

```typescript
export interface HITLAdapter {
    send(correlationId: string | number, request: HITLRequest): void;
    onResponse(handler: HITLResponseHandler): void;
}
```

`onResponse` is called by the HITL constructor. The adapter should retain the
handler and call it when the client responds. `send` receives the correlation
id generated by HITL and the complete typed request. The adapter should pass
that id to the client without changing it.

The response must use the same correlation id. HITL uses the id to resolve the
pending request. Responses can arrive in any order when several requests are
active.

## Request And Response Types

The strategy sends one of four request types:

| Request `type` | Triggered by | Client should display | Required response |
|---|---|---|---|
| `tool-approval` | A tool name is present in `toolsUsage` and the tool call reaches the approval flow. In `AutoPilotHITL`, the judge must first return `use-hitl`. | Tool name, description, parameters, and an allow/deny control. | `{ type: "tool-approval", answer: "allow" | "deny" }` |
| `abc-question` | The agent calls `hitl_ask_abc_question`, enabled by `questions.abcQuestion`. The tool calls `emitAbcQuestion()` directly. | The question and one selectable control for each `[optionKey, optionLabel]` tuple. | `{ type: "abc-answer", option, optionLabel }` |
| `open-question` | The agent calls `hitl_ask_open_question`, enabled by `questions.openQuestion`. The tool calls `emitOpenQuestion()` directly. | The question and a free-text input. | `{ type: "open-answer", answer }` |
| `acceptance` | Application or skill code calls `emitAcceptance()`, or the agent calls `hitl_ask_acceptance` when `accetpanceAsTool` is enabled. | The question, optional context, and an allow/deny control. | `{ type: "acceptance-answer", answer: "allow" | "deny" }` |

The complete shapes are:

```typescript
export type HITLRequest =
    | {
        type: "tool-approval";
        toolName: string;
        toolInstance: Tool;
        params: Record<string, any>;
    }
    | {
        type: "abc-question";
        question: string;
        options: [string, string][];
    }
    | {
        type: "open-question";
        question: string;
    }
    | {
        type: "acceptance";
        question: string;
        context?: string;
    };

export type HITLResponse =
    | { type: "tool-approval"; answer: "allow" | "deny" }
    | { type: "abc-answer"; option: string; optionLabel: string }
    | { type: "open-answer"; answer: string }
    | { type: "acceptance-answer"; answer: "allow" | "deny" };
```

The client must return the response type that corresponds to the request
being answered. The strategy currently resolves the pending request by
correlation id; application-level validation of option keys, labels, and
response/request type should also be performed by a production adapter or
client boundary.

## Trigger And Event Flow

The adapter receives a request only after the corresponding strategy method
has been selected:

```text
ordinary configured tool
    -> ReActAgent sees tool name in toolsUsage
    -> HITL.emitToolUsage()
    -> AutoPilotHITL may judge the tool
    -> adapter.send(id, { type: "tool-approval", ... })

agent question tool
    -> createQuestionTools() tool handler
    -> emitAbcQuestion() or emitOpenQuestion()
    -> adapter.send(id, { type: "abc-question" | "open-question", ... })

acceptance
    -> emitAcceptance() directly or through hitl_ask_acceptance
    -> optional AutoPilot acceptance judge
    -> adapter.send(id, { type: "acceptance", ... })
```

The following strategy events are emitted for observers through `onEvent` and
`onAnyEvent`; they are not separate adapter requests unless the application
chooses to forward them itself:

| Event | Source | Meaning |
|---|---|---|
| `hitl_start` | `emitToolUsage`, `emitAbcQuestion`, `emitOpenQuestion`, or `emitAcceptance` | A HITL interaction started. |
| `hitl_end` | The corresponding flow after a response or approval timeout | The HITL interaction finished. |
| `hitl_request_sent` | After `adapter.send()` | A request was handed to the adapter. Includes `id` and `HITLRequest`. |
| `hitl_response_received` | `handleResponse()` | A response with a matching correlation id was received. |
| `hitl_tool_call` | `emitToolUsage()` | An ordinary tool approval is being requested. |
| `hitl_tool_result` | `emitToolUsage()` | An ordinary tool approval resolved as allow or deny. |
| `hitl_delay_passed` | Tool approval timeout | A configured approval timeout resolved or rejected the approval. |
| `hitl_acceptance_started` | `emitAcceptance()` | An acceptance request is beginning. |
| `hitl_acceptance_received` | `emitAcceptance()` | An acceptance response was received. |
| `autopilot_judge_started` | `AutoPilotHITL` tool judge | AutoPilot started judging an ordinary configured tool. |
| `autopilot_judge_finished` | `AutoPilotHITL` tool judge | AutoPilot finished with `use-hitl` or `omit`. |

Register observers on the concrete strategy:

```typescript
hitl.onEvent("hitl_request_sent", (id, request) => {
    console.log("HITL request sent", id, request.type);
});

hitl.onAnyEvent((eventName, ...args) => {
    console.log("HITL event", eventName, args);
});
```

For AutoPilot, `autopilot_judge_*` events apply to the ordinary
`emitToolUsageAutoPilot` path. The built-in question tools do not enter that
judge path. Acceptance uses its dedicated optional judge when
`engageJudgeInEmittingAccetpance` is enabled.

## Writing A Custom Adapter

A custom adapter can use any local or network transport. It may send requests
over IPC, WebSocket, HTTP, a message queue, or an application callback. The
minimum implementation is:

```typescript
import {
    HITL,
    HITLAdapter,
    HITLRequest,
    HITLResponse
} from "@ravenlens/raven-adk/tools/hitl";

class MyHITLAdapter implements HITLAdapter {
    private responseHandler?: (
        correlationId: string | number,
        response: HITLResponse
    ) => void;

    onResponse(handler: (
        correlationId: string | number,
        response: HITLResponse
    ) => void): void {
        this.responseHandler = handler;
    }

    send(correlationId: string | number, request: HITLRequest): void {
        // Send this envelope to the UI or client through your transport.
        client.send({ id: correlationId, request });
    }

    receiveFromClient(
        correlationId: string | number,
        response: HITLResponse
    ): void {
        // Call the handler with the original id when the client answers.
        this.responseHandler?.(correlationId, response);
    }
}

const adapter = new MyHITLAdapter();
const hitl = new HITL({
    adapter,
    toolsUsage: { delete_account: true },
    questions: {
        abcQuestion: { instruction: "Ask concise choice questions." },
        openQuestion: { instruction: "Ask only when choices are insufficient." }
    }
});
```

A real adapter should also:

- Preserve the correlation id exactly across the transport boundary.
- Route responses by request type and render the appropriate UI control.
- Avoid sending a response before the request has been delivered to the user.
- Treat request data as untrusted input when rendering tool descriptions and
  parameters.
- Handle disconnects, duplicate responses, malformed responses, and client
  timeouts according to the application's policy.
- Avoid exposing secrets contained in tool parameters to an unintended client.
